# 멀미케어 v2 설계: 프로필 개인화 · 즉시 케어 · 완성도

작성: 2026-11-02 · 목표 완료: 2026-11-14 (1차 접수 마감 11/15 하루 전)

## 1. 의도

1차 제출(11/15) 전에 데모 수준의 앱을 **실제 차량에 탑재된 앱처럼 보이고, 오류 없이 동작하는 앱**으로 끌어올린다.
기획서에 "2차까지 추가 개발"로 적어 둔 기능을 실제로 구현해서 기획서를 "구현 완료"로 바꿔 쓸 수 있게 하고,
자주 타는 동승자는 **프로필**로 개인화한다. 처음 타는 사람·택시 승객은 **게스트**로 바로 쓴다.

## 2. 목표 · 비목표 · 실패 조건

**목표**
1. 프로필(여러 명) + 게스트. 프로필은 주행이 쌓일수록 그 사람에게 맞게 조절된다.
2. "속이 안 좋아요": 한 번 누르거나 말하면 즉시 케어 + 가까운 휴게소 경유 제안.
3. 주행 기록 저장과 주행 리포트 화면(점수 추이, 학습 결과).
4. 내비 안내 기반 회전 예고(방향지시등보다 먼저).
5. Pleos UI 가이드를 따른 화면: 주간/야간, 세로/가로, 큰 터치 영역.
6. 오류·버그 없음: 아래 8장의 검증 항목을 모두 통과.

**비목표**
- 서버, 로그인, 클라우드 동기화 (데이터는 차 안에만 저장).
- 운전자 프로필 (운전자에게는 지금처럼 음성 코칭만).
- 실제 택시 플랫폼 연동 (전송 데이터 미리보기까지만).
- 음악 재생, 회생제동 단계 직접 제어 (SDK에 제어 API 없음).

**실패 조건** (동작해도 실패로 본다)
- 주행 중 운전자에게 키보드 입력·복잡한 조작을 요구한다.
- 학습 결과가 사용자에게 보이지 않거나 되돌릴 수 없다.
- 게스트 데이터가 저장된다.
- 화면이 여전히 "개발용 테스트 화면"처럼 보인다.

## 3. 제약 (확인한 사실)

- **Pleos UI 가이드**: 주간/야간 모드 지원, 텍스트 최소 18px(핵심 정보 5mm), 대비 4.5:1 이상, 한 문장 3줄 이내,
  입력 후 0.25초 안에 반응, 주행 중 동영상·장식 애니메이션 금지, 한 손 조작, 시스템 글꼴 Asta Sans.
- **화면 모델**: 기본은 세로(창 1개), 가로(창 2개)로도 실행될 수 있음 → 두 레이아웃 모두 설계.
- **주행 규제(CarUxRestrictions)**: 주행 중 키보드·설정 입력 제한 → 프로필 생성·편집은 정차(P) 중에만.
- **시트 이동**: P단이 아니면 오류 50001로 거부(확인함) → 지금처럼 P단에서만.
- **성능**: 주행 중 CPU 5% 미만, RAM 400MB 이하. 백그라운드에서 불필요한 갱신 중단.
- **NaviHelper SDK 3.0.5**: `addWaypoint(위도, 경도, 이름…)`, `onTBTInfo(회전 종류, 남은 거리)` 제공. **장소 검색 없음**.
- **SpeechToText SDK 3.3.1**: ON_DEVICE 모드는 네트워크·앱 등록 불필요. 권한 `STT_SERVICE`. 명령 실행은 앱이 직접.
- **개인정보**: 별칭만 저장(실명 불필요), 프로필 삭제 쉽게, 차 밖으로 나가는 데이터 없음.
- **기간**: 약 12일. 기존 구조(Kotlin + 코드로 만든 View, 의존성 최소)를 유지한다.

## 4. 접근 방식 (선택 완료)

| 방식 | 내용 | 장단점 |
|---|---|---|
| A. 기획서 약속 먼저 | 휴게소·음성·설문·기록 4개 구현 | 기획서와 일치 / 화면 인상은 약함 |
| B. 시연 인상 먼저 | 실주행 동기화 시연, 화면 추가 | 영상이 좋아짐 / 기능은 그대로 |
| **C. 핵심 결합 (선택)** | 음성+휴게소 흐름, 기록·리포트, 설문, 영상 재녹화 | 차량특화성·사업성을 직접 보여줌 / 음성·내비 에뮬레이터 동작은 먼저 시험 필요 |

사용자가 **C**를 고르고 **프로필 개인화**를 추가했다.

## 5. 기능 설계

### 5.1 화면 구성
한 Activity 안에서 화면을 바꾼다(뒤로가기 지원).

1. **탑승자 선택** (앱 첫 화면)
   - 프로필 카드(별칭, 자리, 최근 점수) + **게스트로 시작** + **새 프로필**(P단에서만, 주행 중엔 이유 표시).
   - 마지막에 쓴 프로필이 맨 앞. 카드를 누르면 바로 주행 화면으로.
2. **프로필 만들기** (P단에서만)
   - 별칭(키보드) → 자리(동승석 / 뒷좌석 왼쪽 / 뒷좌석 오른쪽) → 멀미 설문 3문항 → 완료.
3. **주행** (지금 화면을 다듬은 메인)
   - 위험 지수 + 그래프, 지금 하는 케어, **"속이 안 좋아요" 큰 버튼**, 마이크 버튼, 현재 탑승자 표시.
4. **주행 리포트** (주행 종료 시)
   - 점수, 멀미 피드백(0~10), "도움 된 케어" 선택(선택 사항), 학습 결과 한 줄, 택시 전송 미리보기.
   - 게스트면 "프로필로 저장" 제안(P단에서만).
5. **프로필 상세**
   - 최근 10회 점수·멀미 추이, 학습 상태(경고 시점, 케어별 효과, 선호 온도), 케어 켜기/끄기, 프로필 삭제.

### 5.2 프로필과 학습
- **저장 위치**: 앱 내부 저장소의 JSON 파일 하나. 게스트는 메모리에만.
- **프로필 데이터**: id, 별칭, 자리, 민감도, 선호 케어 온도, 케어별 기록(실행 횟수·도움 횟수·꺼짐 여부), 최근 주행 50개(날짜, 시간, 점수, 최고 단계, 멀미 피드백, 실행된 케어).
- **설문 → 초기 민감도**: 3문항(차 멀미 빈도, 책·화면 볼 때 멀미, 뒷좌석 멀미) 각 0~2점, 합계 0~6 → 민감도 0.8 / 1.0 / 1.3.
- **학습 규칙** (단순하고 설명 가능하게, 모두 단위 테스트):
  1. *경고 시점*: 멀미 4 이상인데 "위험" 단계에 못 갔으면 민감도 ×1.1(더 일찍), 멀미 1 이하인데 "위험"까지 갔으면 ×0.9(더 늦게). 범위 0.5~2.0. 화면에는 "기본보다 20% 일찍 경고"처럼 표시.
  2. *케어 효과*: 케어가 3번 이상 실행됐는데 "도움 됐어요"가 1/3 미만이면 그 케어를 꺼 두고 프로필 화면에 "효과가 적어 꺼 둠 · 다시 켜기"를 표시. 사용자가 다시 켤 수 있다.
  3. *선호 온도*: 주행 중 사용자가 직접 바꾼 온도(앱이 바꾼 값 제외)를 18~26°C 범위에서 기억해 다음 공기 케어 온도로 쓴다.
- **게스트**: 기본값(민감도 1.0, 21°C, 모든 케어 켜짐), 아무것도 저장하지 않음.

### 5.3 "속이 안 좋아요" 즉시 케어
- **입력**: 큰 버튼 한 번, 또는 마이크 버튼을 누르고 말하기(STT ON_DEVICE). 인식 단어: "속", "멀미", "어지러", "토할", "메스꺼", "울렁".
- **동작**: 공기 케어 + 호흡 가이드를 즉시 시작하고 음성으로 안내.
- **휴게소 제안**: 현재 위치에서 가장 가까운 휴게소를 찾아 "○○휴게소까지 12km, 경유지로 추가할까요?"를 묻는다. 예/아니요는 큰 버튼 또는 음성으로 답한다. 예면 `addWaypoint`.
- **위험 단계 자동 제안**: 위험 단계가 3분 넘게 이어지면 한 번만 같은 제안을 한다.
- **휴게소 데이터**: OpenStreetMap의 국내 고속도로 휴게소(이름, 좌표)를 앱 리소스로 넣는다(ODbL, 앱 정보에 출처 표기).
- **대체 동작**: 내비 연결 실패, 근처 50km 안에 휴게소 없음, 음성 인식 실패 시 각각 한 줄로 안내하고 케어는 계속한다.

### 5.4 내비 기반 회전 예고
- `onTBTInfo`의 다음 회전이 좌·우·급회전·유턴이고 남은 거리가 300m 아래로 내려오면 한 번 예고("300m 뒤 왼쪽으로 돌아요").
- 경로 안내가 없으면 지금처럼 방향지시등으로 예고한다.

### 5.5 주행 기록과 리포트
- 주행이 끝나면 기록을 저장한다(프로필만). 리포트는 최근 10회 점수를 막대로, 멀미 피드백을 점으로 보여준다.
- 택시 전송 미리보기는 지금처럼 유지한다.

### 5.6 디자인 방향
- **디자인 도구 (사용자 요청)**: 설치된 디자인 스킬을 사용한다.
  - `design-taste-frontend`의 앱 화면 절차를 따른다: 화면마다 "한 가지 질문" 정하기 → 스타일 뽑기(야간은 기존 `true-black-flat`, 주간은 `--theme light`로 새로 뽑음) → 화면 구현 → 스크린샷으로 비평 체크리스트 7항목 확인 → 상위 3개 수정, 최대 3회 반복.
  - octo 플러그인의 `ui-ux-designer` 에이전트로 디자인 토큰(색·글자·간격)과 컴포넌트 명세를 만들고, 완성 화면 스크린샷을 검토받는다.
  - 두 스킬의 결과가 Pleos UI 가이드와 다르면 Pleos 가이드를 따른다(실제 차량 규칙이므로).
- **참고**: Pleos 시스템 화면(밝은 바탕, 큰 둥근 카드, 절제된 색) + Pleos UI 가이드 규칙.
- **주간/야간**: 시스템 설정을 따른다. 주간은 밝은 바탕, 야간은 지금의 어두운 바탕.
- **색**: 데이터 색은 하늘색 하나, 상태 색(편안·주의·위험)은 상태에만.
- **글꼴**: 시스템 기본(Pleos 이미지에 Asta Sans가 있으면 그대로 쓰임). 숫자는 고정폭 숫자.
- **글자**: 본문 22 / 보조 18 이상(최소 18px 지킴), 한 문장 3줄 이내.
- **터치**: 버튼 높이 64dp 이상, 간격 16dp 이상. 누르면 즉시 눌림 표시(0.25초 규칙).
- **아이콘**: 단순한 선 아이콘(벡터)을 라벨과 함께 사용한다.
- **세로/가로**: 세로는 위험 지수 → 케어 → 즉시 케어 버튼 순서로 한 열, 가로는 지금처럼 2열.
- **움직임**: 주행 중 장식 애니메이션 없음. 그래프는 값이 바뀔 때만 다시 그린다.

## 6. 코딩 원칙 (사용자 요청: ponytail 모드)
- 필요한 것만 최소한으로 만든다. 구현체 하나뿐인 인터페이스, 쓰지 않는 확장 포인트, "나중을 위한" 구조는 만들지 않는다.
- 새 라이브러리를 추가하지 않는다. JSON 저장은 Android 내장 `org.json`, 그래프는 기존 Canvas 그리기를 쓴다.
- 이미 있는 코드(`Comfort`, `Ui.kt`의 도우미, `TraceView`)를 재사용하고, 파일 수는 최소로 유지한다.
- 의도적으로 단순화한 부분에는 한계와 개선 방법을 적은 `ponytail:` 주석을 남긴다.
- 단순화하지 않는 것: 입력 검증, 데이터 손실 방지(저장 안전성), 안전 규칙(P단·주행 규제), 접근성 기본, 요청받은 기능.
- 테스트도 최소한으로: 분기·계산이 있는 로직마다 깨지면 실패하는 테스트 하나씩.

## 7. 안정성 (버그 없는 앱을 위한 원칙)
- **로직과 화면 분리**: 학습·저장·키워드 인식·휴게소 찾기·회전 예고 판단은 Android에 의존하지 않는 순수 Kotlin으로 만들고 단위 테스트한다.
- **스레드**: SDK 콜백은 메인 스레드로 넘겨서 화면을 갱신한다.
- **생명주기**: 백그라운드로 가면 화면 갱신을 멈추고, 돌아오면 복원한다. 진행 중 주행은 프로세스가 재시작돼도 복원한다(저장 파일).
- **SDK 실패 대비**: 모든 SDK 기능은 지원 여부를 먼저 확인하고, 실패하면 해당 카드에 한 줄 안내만 띄운다(앱 종료 금지).
- **음성 겹침 방지**: 안내 음성은 순서대로 재생하고, 같은 안내는 30초 안에 반복하지 않는다.
- **저장 안전성**: 임시 파일에 쓴 뒤 교체해서, 쓰는 중에 꺼져도 파일이 깨지지 않게 한다.

## 8. 검증
- 단위 테스트: 기존 6개 + 학습 규칙, 설문 점수, 저장/불러오기, 키워드 인식, 가까운 휴게소 찾기, 회전 예고 판단.
- 에뮬레이터 확인 목록: 프로필 생성/선택/삭제, 게스트 → 프로필 저장, 주행 중 생성 차단, 속이 안 좋아요(버튼·음성), 휴게소 경유지 추가, 내비 회전 예고, 리포트·학습 반영, 주간/야간, 세로/가로, 백그라운드 복귀, 시트 P단 규칙.
- release APK로 최종 확인 후 GitHub 푸시, 시연 영상 재녹화, 기획서 갱신.

## 9. 결정 기록
- **사용자 결정**: 방향 C, 프로필 + 게스트, 프로필 학습 3가지(경고 시점·케어 효과·선호 온도), 차 안 저장, 운전자 프로필 없음, Pleos 실제 차량 앱 수준 디자인, 버그 없음.
- **내 결정 (바꿀 수 있음)**:
  - (사용자 결정) 디자인은 설치된 디자인 스킬로, 코딩은 ponytail 모드로 한다.
  - 화면 기술은 지금처럼 코드로 만든 View를 쓴다(Compose 도입 안 함). 기간 안에 재구성 위험을 줄이기 위해서.
  - 휴게소 데이터는 OpenStreetMap에서 가져온다(공공 API는 키 발급이 필요해서).
  - 케어 효과는 주행 후 "도움 된 케어" 선택(선택 사항)으로 받는다. 멀미 점수만으로는 어떤 케어가 도움 됐는지 구분할 수 없기 때문이다.
  - 위험 단계 3분 지속 시 휴게소를 자동 제안한다.
  - 등받이·공조는 프로필의 자리에 맞는 좌석 구역을 쓴다. 그 자리를 차량이 지원하지 않으면 해당 버튼을 숨긴다.
  - 데모 주행도 프로필 기록에 저장하되 "데모"로 표시한다. 시연에서 학습·리포트 흐름을 보여주기 위해서다. 실제 데이터처럼 꾸민 가짜 기록은 넣지 않는다.
  - 에뮬레이터 시연 때는 위치를 국내 고속도로 위로 설정한다(`adb emu geo fix`). 기본 위치는 미국이라 휴게소가 잡히지 않는다.
- **구현자 재량**: 정확한 색 값, 아이콘 모양, 리포트 그래프 세부 모양, 파일 구조.
